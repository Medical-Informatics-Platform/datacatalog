# Repository Guidelines

## Project Structure & Module Organization
This repository is split by service. `frontend/` contains the Angular 22 UI (standalone bootstrap in `frontend/src/main.ts`); application code lives in `frontend/src/app`, assets in `frontend/src/assets`, brand rules in `frontend/src/DESIGN_SYSTEM.yaml`, and specs next to components as `*.spec.ts`. `backend/` is a Spring Boot 4.1 (Java 21) service with sources in `backend/src/main/java/ebrainsv2/mip/datacatalog`, dev config and Flyway migrations in `backend/src/main/resources` (`db/migration`), the container config template in `backend/config/application.tmpl`, and tests in `backend/src/test/java`. `data_quality_tool/` is a Python 3.12 Flask service for Excel and JSON conversion and validation. Root-level `compose.yaml` starts the local stack, `kubernetes/` contains the Helm chart, and `.github/workflows/` holds the data quality tool CI, the release image build driven by `.github/workflows/docker-bake.hcl`, and the EBRAINS GitLab mirror.

## Build, Test, and Development Commands
Run the full stack from the repository root with `docker compose up --build`. For frontend-only work: `cd frontend && npm ci && npm start`; use `npm run build` for a production bundle in `dist/datacatalog-frontend` and `npm test -- --watch=false --browsers=ChromeHeadless` for CI-style tests; Angular CLI 22 requires Node `^22.22.3 || ^24.15.0 || >=26.0.0`. For backend work you need JDK 21: `cd backend && mvn test` or `mvn spring-boot:run`. `mvn spring-boot:run` reads `backend/src/main/resources/application.yml`, which points at the Compose host names, so host-local runs pass Spring properties through `-Dspring-boot.run.arguments` (`spring.datasource.*`, `spring.flyway.*`, and `app.data_quality_tool.*-url`); `application.yml` ships `authentication.enabled: 0`, so pass `authentication.enabled=1` with a real `keycloak.client-secret` to test the OIDC login flow; `DB_URL`, `PUBLIC_HOST`, and `DQT_URL` are only read by the container image through `backend/config/application.tmpl`. For the data quality tool: `cd data_quality_tool && poetry install --with dev`, then `poetry run python controller.py`, `poetry run pytest`, and `poetry run black .`. Build images locally with `docker buildx bake -f .github/workflows/docker-bake.hcl`.

## Coding Style & Naming Conventions
Follow `frontend/.editorconfig`: UTF-8, spaces, 2-space indentation, and single quotes in TypeScript. Keep Angular naming consistent with the existing tree, for example `header.component.ts`, `auth.service.ts`, and `user.interface.ts`. In Java, keep package names lowercase, classes in PascalCase, and methods and fields in camelCase. Place backend code in the matching domain package such as `datamodel`, `federation`, or `user`. Python code should stay `black`-formatted and use snake_case for modules, functions, and tests.

## Testing Guidelines
Add tests with every behavior change. Frontend tests belong beside the component or service they cover and should follow the `*.spec.ts` pattern. Backend tests use JUnit under `backend/src/test/java`; prefer focused coverage for converters, validators, and service logic, and keep them plain unit tests because the suite has no `@SpringBootTest` context and CI does not start a database. Python tests live in `data_quality_tool/tests` and should cover both happy paths and malformed Excel or JSON inputs. CI runs the Python suite with `pytest` plus `coverage` and uploads to Codecov only when `CODECOV_TOKEN` is set, so no coverage gate is enforced and reviewers will expect targeted regression tests in changed areas.

## Commit & Pull Request Guidelines
Recent history favors short, prefixed subjects such as `feat: ...`, `Fix: ...`, and `chore(scope): ...`; keep commits imperative and scoped to one change. Pull requests should summarize the affected module, list the commands you ran, and link the issue or ticket when available. Include screenshots for frontend UI changes and call out any `.env`, Keycloak, Docker, or Helm impact.

## Configuration Tips
Keep local secrets in `.env` (git-ignored; `.env.example` is the tracked template) and Kubernetes secrets, never in tracked files. Do not commit generated frontend output from `frontend/dist/` or local Postgres data under `.stored_data/`. When changing database image versions or mount paths, update `compose.yaml` and the Helm files together so local and cluster deployments stay aligned. Keep backend keys in sync between `backend/src/main/resources/application.yml` and `backend/config/application.tmpl`, which is the version rendered by `dockerize` in the image. CSRF protection is on for every profile, including `AUTHENTICATION=0`: the backend issues the `MIP-XSRF-TOKEN` cookie and expects the `X-MIP-XSRF-TOKEN` header, which the Angular client sets through `withXsrfConfiguration` in `frontend/src/main.ts`. Data quality tool validation errors go through `error_reporting.client_error_message`, which keeps the client response to one bounded line and never echoes a stack trace; keep unexpected failures on the logged generic-500 path.
